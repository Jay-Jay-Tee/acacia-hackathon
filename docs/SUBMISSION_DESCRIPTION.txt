AD FINDER
Traceable answers from FAA airworthiness directives, with every claim cited and applicability checked by code
Airbus track, Challenge #4: "How might AI help people find, understand, and verify regulated technical information?"


THE PROBLEM

A maintenance technician or engineer needs to know three things quickly: which airworthiness directives (ADs) cover this aircraft, what each one requires, and whether it applies to this particular serial number. Today the answer means searching the Federal Register by hand and reading dense legal text. A general chatbot is faster, but it makes things up. It can mix instructions from one model into another, invent compliance intervals, or treat a withdrawn proposal as if it were a binding rule. In maintenance, one confident wrong answer such as "this AD does not apply to your aircraft" can lead to a serious incident.

AD Finder treats trust as the main requirement rather than an extra. It answers only from the source documents, cites every sentence, leaves the legally important decisions to deterministic code, and says "I can't answer that" rather than guess.


WHAT IT DOES

Find
- Search 431 FAA AD notices (about 1,295 Federal Register pages, 8,971 searchable passages) in plain English or by docket or AD number.
- Hybrid retrieval: BM25 keyword search (SQLite FTS5) combined with local embeddings (bge-small, no external API), narrowed by the aircraft model the user selects.
- Aviation query expansion, so that "winch" also finds "hoist" and "HPT" also finds "high-pressure turbine".
- Retrieval latency of about 12 ms (median) and 19 ms (95th percentile).

Understand
- Claude writes a short answer using only the retrieved passages, with native citations.
- Each answer block shows the record ID, docket, Federal Register citation, page, section, revision date and the verbatim quote it relies on.
- A revision timeline groups each docket's notices. The notice with the latest publish date is treated as the current version, and withdrawals are shown as withdrawals.
- A fixed status notice, generated by code, appears whenever a cited document is a proposed rule (NPRM), a withdrawn proposal, or not an AD at all. Most of the corpus is proposals, and the user is always told.

Verify
- Applicability is decided by code, not by the LLM. Model lists and serial-number rules (ranges, "except" clauses, lists, "and subsequent", engine serial numbers) give one of four verdicts: APPLIES, DOES_NOT_APPLY, UNKNOWN or AMBIGUOUS, each with a readable trace of how it was reached.
- If a rule can't be parsed (for example serials listed in a table, a service bulletin, or a foreign AD), the verdict is UNKNOWN and the trace says why.
- A source viewer opens the full Federal Register text with the cited passage highlighted.
- Fleet check: upload a CSV of tail numbers, models and serials and screen the whole fleet in one pass.
- Compliance note export: a Markdown record of the question, the answer, every citation and quote, the applicability trace, a timestamp, and a line for certifying-staff review.
- PDF upload: ask cited questions over your own manuals. Answers over uploaded documents are extractive quotes only and never pass through the LLM, so an uploaded file can't inject instructions.


HOW IT STOPS HALLUCINATION AND CROSS-EQUIPMENT BLENDING

The rule is simple: code decides retrieval, applicability, revisions and refusals, and the LLM only phrases an answer from passages it has been given. There are three layers of protection, and none of them relies on the model behaving well.

1. Before the LLM. A relevance gate refuses the question unless a retrieved passage actually covers it. Separate gates catch out-of-scope questions, ambiguous model names (for example "A320" gets clickable candidate models, not a guess), premises that contradict the applicability verdict (such as a serial outside the AD's range), requests to skip a mandatory action, and attempts to probe or override the assistant.
2. During the LLM call. Claude sees only the retrieved documents, with citations turned on, and is told to reply "the provided documents do not answer this" when they don't.
3. After the LLM call. Code removes any sentence that has no citation, or that contains a number, part number or serial that doesn't appear in its cited text. If nothing survives, the question is refused. If Claude errors, declines or is unavailable, the system falls back to extractive mode: verbatim cited passages with no generated prose, clearly labelled as such.

Because the user's aircraft model filters retrieval and applicability is checked per document by code, an answer about one model can't quietly borrow instructions written for another.


RESULTS

Measured with the scripts in evaluation/. Full method in docs/EVAL.md. The human-written sets are small and were written by the team, so they are not blind.
- Applicability, synthetic: a listed model was never wrongly excluded (206/206), an unlisted sibling model was always excluded (165/165), and withdrawn proposals were never reported as applying (183/183).
- Applicability, human-written serial edge cases: 14/14.
- Retrieval recall@5 on human-written questions: 78/79 with the aircraft model given, 60/63 without.
- Ambiguous model names sent back for clarification: 8/8. Prompt-injection attempts refused: 5/5, plus a dedicated test suite.
- Citation coverage of generated answer blocks: 100%.
- Full answer with Claude: about 4 to 5 seconds (near-instant when cached). 138 automated tests pass.

We picked the answer model by measurement. Opus 5.5 at low effort matched medium and high effort, and Fable 5.1, on accuracy, while being the fastest and having the fewest sentences removed by the citation check. A bigger model adds nothing when its only job is to phrase retrieved text.


WHERE IT FAILS, AND HOW THE USER KNOWS

The system is built to fail towards refusing, towards UNKNOWN, or towards showing a quote the reader can check. It never fails towards a confident answer with no citation.
- Its main weakness is over-refusal. 11 of 39 answerable human-written questions are refused, mostly symptom-style wording such as "stick shaker firing for no reason". This costs the technician time, not safety. Setting the aircraft model or searching by docket fixes most cases.
- 4 of 12 aviation-adjacent off-topic questions get through the gate. They are shown only as labelled extractive quotes, so it is visible that the passages don't address the question.
- The applicability parser returns UNKNOWN on about a quarter of synthetic cases (table-based serials, configuration conditions, delegation to a foreign AD) and hands those back to a person.
- We found and handled problems in the source data itself. For 169 rows, the index's link points to a different notice in the same docket than the one the row cites. Citations are therefore keyed on the cited page, which matches for 382 of 389 rows. One record's summary describes an unrelated rule, and it is flagged on its card.


WHY IT MATTERS

AD Finder is decision support, not a decision maker. Certifying staff still sign off, but they start from the right documents, the right revision, a verdict with its reasoning shown, and a quote behind every sentence. It speeds up finding, explains the documents in plain language, and gives verification a clear audit trail instead of asking the engineer to trust the AI.


BUILT WITH

Python, FastAPI, SQLite FTS5, local bge-small embeddings, Claude (claude-opus-5-5) with native citations, and React + TypeScript (Vite). Data: the organisers' FAA AD spreadsheets plus Federal Register full text fetched by script (US government works, public domain). Code is MIT licensed.
